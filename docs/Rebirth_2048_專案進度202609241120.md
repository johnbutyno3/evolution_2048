# 10. 本輪新增修正（Save race）

發現 Restart 閃回舊棋盤仍可能來自 local autosave race：舊 GameEngine 與新 GameEngine 各自排程 SaveManager.save，兩條寫入路徑可能交錯，導致舊 snapshot 最後覆蓋新棋盤。

已於 `685866143fe81bded76a7ae9942284f88dfe21ca` 修正：

- SaveManager 所有 snapshot write 改為全域序列化 queue。
- 舊 engine queued autosave 不會再與新 engine save 同時競爭。
- Restart 新 session rebinding 與 local save serialization 現在同時受保護。
- 此項仍待與 Restart / Game Over → Restart 一次實機驗證。

# 21. Expired Resume 與新 Session 初始棋盤一致性補強（2026-09-24）

本輪檢查發現本機仍有可玩 cached board，但 server active session 可能已 TTL expired。不能把舊 board 直接綁到 replacement session，否則新的 server session 與實際 replay 起點可能不一致。

已修正：

- `resumeGameSession` 遇到 expired session 不再自行建立缺少 initialTiles 的 replacement session，而是回報失敗給頁面層。
- 遊戲頁收到 resume failure 後，會建立全新 board，取得該 board 的 exact `initialTiles`，再建立 replacement session。
- 新 board 與 server session 使用完全相同的 initialTiles，舊 cached board 不會被重新綁到新 session。

# 22. Local-first Session 失敗後的完成結算恢復（2026-09-24）

繼續檢查「Firebase 背景建立 Session 失敗，但玩家已經開始遊戲」路徑後，確認一般進場不能等待網路；但玩家若在背景 Session 尚未成功時快速完成遊戲，不能讓完成棋盤變成無法結算的孤立局。

- 正常情況仍維持 local-first，進場不等待 Firebase。
- 若背景 `startGameSession` 已失敗且沒有 active session，完成時會從本次 replayLog 取得**原本實際使用的 initialTiles**。
- 以相同 initialTiles 建立新的 server session，再進行正常 `completeChapter` 結算。
- 若原本的背景請求其實已經在 Firebase 成功、只是回應遺失，既有 start/reconciliation 邏輯會先辨識 server active session，不會任意把本局當成失敗。
- 不使用完成後的棋盤重新建立 Session，避免 Replay 起點與 server 綁定不一致。

# 23. 防止並發進場造成重複扣命（2026-09-24）

檢查 Life / Session race condition 後發現：一般新局第二次呼叫會因 active session 被 Server 擋下，但在第一個 local-first `startGameSession` 尚未完成背景交易期間，若同時觸發第二次呼叫，兩個 Firebase transaction 在特定 `replaceActiveSession` 情境下仍可能形成重複 Session／Life 扣除風險。

已在 `PlayerProgressService.startGameSession()` 加入 `_pendingStartSession` guard：

- 第一個 start 立即消耗本機 Life 並開始背景 Firebase transaction。
- 同期間第二次 start 直接視為同一個進場操作，不再次 optimistic 扣 Life，也不再送第二個 Firebase start transaction。
- 不等待網路，因此不破壞 local-first 進場速度。
- 真正的 Server session 仍只有第一個請求負責建立與結算。

實際提交：
- `87ef7a79b7ee3e3e2706c7c5fa24a5368d49bc65` — prevent duplicate concurrent game starts。

# 24. 背景 Start 失敗後的 Completion Recovery race 修正（2026-09-24）

- Completion recovery 在確認上一個背景 start 已失敗後，可真正重新送出新 Session 建立。

# 27. Local-first duplicate start latency cleanup（2026-09-24）
