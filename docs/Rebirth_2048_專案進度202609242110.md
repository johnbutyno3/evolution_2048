# 33. Life 倒數到期後的 stale Firebase 回寫修正（2026-09-24）

## 實際問題

實機已觀察到：遊戲中 Life 從 4 倒數到 `00:00` 後，本機先恢復 1 命，但 Firebase `getLifeState` 的背景回應可能仍回傳尚未完成 regeneration 的舊狀態，進而把畫面從 `5`（或應有的新值）重新寫回 `4`。

這與「本機先運行、Firebase 背景確認」的設計方向衝突，也是先前出現 `3 → 4`、`4 → 5 → 4` 類型異常的重要競態來源。

## 已完成程式修正

提交：`4c0ad404b5418fb2dedc3ac72011fb6a99ca4f7a` — `fix: prevent stale life regeneration rollback`

`lib/game/services/life_manager.dart` 現在：

- Life 倒數到期仍由本機立即完成 regeneration，不等待 Firebase。
- regeneration 的背景 `getLifeState` 讀取有獨立 generation 標記。
- 若在 regeneration 讀取期間已有更新的 Session / Life mutation 回應，舊 regeneration response 直接丟棄。
- 若沒有更新的 mutation，但 Firebase 回傳的 Life 仍低於剛完成本機 regeneration 的值，不會立即把本機 Life 回寫降低。
- 一般 server mutation 仍透過 authoritative `applyServerState()` 正常覆蓋本機狀態，因此不是把 Firebase 權威驗證取消。
- Membership、life mode、server regeneration timestamp 等其他 authoritative 欄位仍會同步。

## 與原規則一致

本次沒有改變 Life 規則：

- 一般會員上限 5。
- 低於上限每 40 分鐘恢復 1。
- Golden 為 Infinite Lives。
- 遊戲操作不等待 Firebase。
- Firebase 仍負責後端權威驗證。
- 暫時性舊 response 不得覆蓋較新的本機 / server mutation 狀態。

# 34. Restart / Game Over Session 狀態檢查結果

本輪重新檢查 GitHub HEAD 後，確認目前 `feature/chapter1-spec-implementation` 的 Restart 流程仍保留：

- 新 `GameEngine` 先建立，保持 local-first responsiveness。
- Firebase `restartGameSession` 建立 replacement session 並扣除新 Life。
- `SaveManager.rebindCachedGameSession()` 將 replacement session ID 與目前章節本機 snapshot 綁定。
- rebind 已加入同一個 save queue，避免 session ID、autosave、clear 操作交錯。
- stale session snapshot 不得在新的 active session 下復活。

目前仍屬**待實機最終驗證**，不可把 Restart / Game Over E2E 標記為已驗證完成。
