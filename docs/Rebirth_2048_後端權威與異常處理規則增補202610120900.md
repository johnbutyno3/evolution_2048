# Rebirth 2048 — 後端權威與異常處理規則增補

> 本文件是新增規則，不取代既有專案規則、Firebase 規範、經濟／會員／Life／Game Session／安全規則。既有規則仍有效；若發現衝突，先記錄並審查，不得自行刪除舊規則。

## 1. 最高原則：遊戲本機優先、權威資料後端優先

1. 棋盤移動、合併、分數暫態、動畫與音效由 Flutter 本機即時處理，不得等待 Firebase round-trip。
2. 本機優先是互動延遲策略，不代表本機資料可覆蓋伺服器權威資料。
3. Gold、購買／交易、會員資格與權限等敏感權威狀態，只能由受保護的伺服器流程判定及修改。
4. Life、Game Session、工具庫存、章節進度、Collection 等一般權威資料，在取得有效、完整、可識別的後端結果後，以後端狀態為準；不得用過期快取覆蓋更新的伺服器狀態。
5. 網路錯誤、逾時、App Check 服務錯誤或 Firebase 暫時不可用，不等於作弊，不得直接當成驗證造假。

## 2. 重要安全驗證：Gold、購買與會員

1. 重要驗證必須在伺服器端完成；客戶端回報或本機快取不得單獨作為定罪或授權依據。
2. 只有在伺服器取得足夠、可稽核且符合既定安全規則的證據，確認重大異常並符合鎖定政策時，才可執行帳號限制／鎖定。
3. 單次請求失敗、資料尚未同步、版本差異、第三方驗證服務暫時失效，不得單獨觸發永久鎖定或直接判定作弊。
4. 必須留下最小必要的安全稽核事件，包括 UID、事件類型、時間、原因、關聯交易／操作 ID、驗證結果與必要的非敏感證據。不得記錄密碼、支付憑證或不必要的個人資料。
5. 鎖定／限制與解除必須由受授權的伺服器端流程執行；客戶端不得自行解除。
6. 玩家對重要驗證結果有異議時，透過既有的雙方留言／問題回報管道另行處理。申訴流程與安全判定分離，必須可追蹤；不得將留言功能直接視為付款或會員狀態的權威來源。
7. 購買必須有伺服器端交易驗證、防重複入帳及可恢復的狀態機。尚未確認的購買只能顯示待確認，不得提前發放 Gold 或會員權益。

## 3. 一般權威資料不一致時

1. 若後端成功回傳有效且完整的權威資料，本機狀態與後端不同時，以後端為準並更新本機快取。
2. 更新必須遵循版本／時間／操作識別規則，避免較晚抵達的舊回應覆蓋較新的資料。
3. Life、Game Session 等具有副作用的命令必須支援冪等操作 ID 或等效的伺服器防重機制；逾時後不得盲目建立新命令或重複扣除。
4. 後端回應無效、缺欄位、版本不明或請求失敗時，不得假裝已取得權威結果；保留最後已知有效資料，標記待同步並按政策重試。
5. 當一般資料與後端不一致時，修正狀態並記錄可診斷資訊；不得僅因一般不一致自動鎖定帳號。若伺服器端驗證確認涉及重大安全風險，才依第 2 節獨立判定。

## 4. 同步與 UI 延遲規則

1. 遊戲核心不得直接依賴 Firebase SDK；透過服務／Repository 介面隔離後端實作。
2. 非關鍵同步採背景非同步處理，有限重試、退避、去重及錯誤隔離，不阻塞棋盤互動。
3. 登入、付款、購買及需要伺服器確認的權限操作，必須清楚呈現 pending／confirmed／failed 狀態；不得把 pending 當成成功。
4. 不得每次滑動、每次合併、每次畫面重建或切頁都呼叫 Firebase。
5. App Check、Authentication、Firestore Security Rules、Callable input validation、server authority、replay validation 與 security enforcement 各司其職，不得互相取代。
6. 不得為了讓功能看似正常而關閉正式環境 App Check 或把安全錯誤 fallback 成成功。

## 5. 必要驗收

- 離線時一般棋盤操作不等待網路；本機已保存棋盤不因同步失敗而清空。
- 後端權威資料回傳成功後，本機衝突資料被正確更新，舊回應不能覆蓋新狀態。
- 重要驗證只有在伺服器端確認並符合政策時才限制帳號；暫時性服務錯誤不直接鎖定。
- 購買／Gold／會員流程能處理 pending、成功、拒絕、逾時、重送與重複交易，且不重複授權或入帳。
- Life／Game Session 在逾時重試、重複請求、切頁與重新登入後不重複扣命、不意外建立第二局、不遺失有效棋盤。
- 測試與部署結果必須如實記錄；未執行的測試不得標記通過。
