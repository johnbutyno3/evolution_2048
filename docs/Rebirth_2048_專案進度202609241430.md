# 9. 本輪新增修正（2026-09-24 14:00）

## Restart local save/session binding

發現 Restart 的另一個底層競態：新棋盤會在 Firebase 回傳新 session ID 前先建立並 autosave，而 SaveManager 當時仍持有舊 session ID。若不重新綁定，下一次 resume 會把新棋盤視為 orphaned board，可能再次建立新局或恢復錯誤狀態。

已於 ff28d286843ed2f39b3989159d71cb03d4307bca 修正：

- Restart 記錄舊 session ID。
- Firebase restart 成功取得新 session ID 後，將目前新棋盤的 local save 重新綁定到新 session。
- 舊 session 仍由 server transaction 標記為 replaced。
- 尚未要求經理立即測試；等本批修正完成後一次驗證。

## TEST Controls 入口

functions/index.js 已確認透過 Object.assign(exports, require('./admin_test')) 匯出 adminGetTestAccountState；前端 Personal Page 也已改用同一 callable 判斷 admin，因此不存在「函式沒有 export」這個問題。新建置後若仍看不到 TEST，下一步再檢查部署版本／callable 回應，不先修改安全權限。

先修程式 → GitHub 提交 → 累積一批 → 再請經理一次實機驗證。不重複要求沒有新程式變更的測試。


# 10. 本輪新增修正（Save race）

發現 Restart 閃回舊棋盤仍可能來自 local autosave race：舊 GameEngine 與新 GameEngine 各自排程 SaveManager.save，兩條寫入路徑可能交錯，導致舊 snapshot 最後覆蓋新棋盤。

已於 `685866143fe81bded76a7ae9942284f88dfe21ca` 修正：

- SaveManager 所有 snapshot write 改為全域序列化 queue。
- 舊 engine queued autosave 不會再與新 engine save 同時競爭。
- Restart 新 session rebinding 與 local save serialization 現在同時受保護。
- 此項仍待與 Restart / Game Over → Restart 一次實機驗證。
