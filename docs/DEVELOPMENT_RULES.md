# Rebirth 2048 開發與協作規則

## 1. Git / GitHub 優先

- 以 GitHub `johnbutyno3/evolution_2048` 的目前分支與實際檔案為主要工作依據。
- 原則上由助理直接在 GitHub / Git 完成工作；只有在權限、工具或檔案操作安全性不足時，才要求經理在本機 PowerShell 執行指令。
- 本機執行完成後，確認結果並在適當工作段落完成 Git 提交與進度同步。

## 2. 進度文件必須累積，不得縮水

- 每完成一個工作段落，都要延續既有完整進度內容，再加入最新變更、決策、驗證結果與下一步。
- 不得用較短的摘要取代原本完整進度。
- 日期／時間更新只能建立新的版本，不得因此刪減歷史與目前有效資訊。
- 不得自行重新解讀成「只保留最近進度」或「摘要即可」。
- `PROJECT_STATUS.md` 已不是目前依據，不得重新建立，也不得把舊版當成現行進度來源。

## 3. 規則與進度的唯一有效依據

- 已淘汰、過期或重複的規則／進度文件，不得繼續當作規格依據。
- 發現明確屬於舊版、重複或已被新文件取代的文件時，應刪除，避免產生多套規則。
- 不得再使用舊的 18 階段生物資料、舊生成 l10n、備份檔或其他已淘汰內容。
- 若檔案庫寫入能力暫時受限，先以 Git `docs/` 作為備援保存；能力恢復後再同步回檔案庫，不要求經理手動搬移。

## 4. 本機 PowerShell 安全規則

- **絕對不得提供會關閉、終止或中斷經理目前 PowerShell／終端機工作階段的指令。**
- 禁止使用 `exit`、`Stop-Process`、`taskkill` 或任何等效的關閉／終止終端機指令。
- 即使檢查失敗、條件不符合、目標文字不存在或腳本發生錯誤，也只能顯示錯誤／警告並保持目前 PowerShell 工作階段開啟。
- 所有要求經理執行的 PowerShell 修改腳本，必須先驗證目標檔案與目標文字確實存在，再進行修改。
- 如果目標不存在、匹配數量不正確或前置條件不成立，**不得修改原檔案**；只輸出清楚的錯誤／警告訊息並讓終端機保持開啟。
- 修改完成後應立即進行語法檢查、`git diff --check` 或其他適當驗證；不得以未驗證的本機修改要求經理直接 commit / push。
- 指令應以安全、可回復、最小修改為原則，避免整檔重建造成資料遺失。

## 5. GitHub 寫入安全

- 更新既有大型程式檔前，必須先取得目前完整檔案內容與 blob SHA。
- 不得因讀取結果被截斷，就自行重建一個不完整檔案後覆蓋原檔。
- 若無法安全取得完整內容，改採本機最小化 patch，或先取得其他可靠的完整內容來源。
- 發現誤寫、破壞或不完整 commit 時，應立即恢復到誤寫前的正確 commit，再繼續工作。
- 未經驗證不得把修改推進目前分支。

## 6. 工作方式

- 優先做最小、可驗證、可回復的修改。
- 每一步都先確認目前實際狀態，不使用猜測取代檔案內容。
- 完成一個工作單元後，更新完整累積進度，並記錄實際 commit、檔案、驗證結果與尚未完成事項。
- 不得因開新對話而縮減、遺失或重新開始既有專案進度。
