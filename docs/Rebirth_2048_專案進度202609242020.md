# 10. 本輪新增修正（Save race）

發現 Restart 閃回舊棋盤仍可能來自 local autosave race：舊 GameEngine 與新 GameEngine 各自排程 SaveManager.save，兩條寫入路徑可能交錯，導致舊 snapshot 最後覆蓋新棋盤。

已於 `685866143fe81bded76a7ae9942284f88dfe21ca` 修正：

- SaveManager 所有 snapshot write 改為全域序列化 queue。
- 舊 engine queued autosave 不會再與新 engine save 同時競爭。
- Restart 新 session rebinding 與 local save serialization 現在同時受保護。
- 此項仍待與 Restart / Game Over → Restart 一次實機驗證。

# 17. 工具 Inventory 同步等待修正（2026-09-24）

檢查 UNDO 初始數量與工具同步資料流後，確認一個實際程式問題：

- ToolManager.refreshInventory() 名義上是背景刷新，但方法本身立即以 unawaited(_refreshInventoryFromServer()) 返回。
- 因此遊戲建立流程中的 await ToolManager.refreshInventory() 實際上沒有等待 Firebase inventory 完成。
- _createGameSession() 雖然寫了「Load the server-authoritative tool inventory before constructing the engine」，實際仍可能在 inventory 回傳前建立 GameEngine。
- 這會造成工具數量在建立遊戲時仍是舊快取／0，之後 server inventory 才到達；但既有 ToolState 不會自動重建，因此畫面可能持續顯示錯誤數量。
- 這與實機觀察到「進遊戲時 UNDO 不是立即 1、之後才出現」的現象一致。

已於 26d40441695b2cc0fc63ffee0a91938787f64045 修正：

- ToolManager.refreshInventory() 改為真正回傳 _refreshInventoryFromServer() Future。
- 需要同步完成的流程現在可以真正 await inventory。
- 本機優先進入遊戲的流程仍可直接使用 unawaited(ToolManager.refreshInventory())，因此不會因此改變「遊戲不得被網路延遲阻塞」的正式原則。
- _createGameSession() 現有的 await ToolManager.refreshInventory() 現在才真正具有效果。
- Server inventory、C1 初始 UNDO、chapter reward 的既有規則未修改。

下一步仍需檢查 GameEngine 建立／工具 UI 使用流程，確認工具狀態是否在 refresh 後正確反映 server cache；完成程式批次後再安排一次實機 E2E，不要求現在單獨測試。


# 18. Restart 後已掛載 ToolState 同步修正（2026-09-24）

進一步檢查 Restart 的工具資料流後發現：即使 `restartGameSession()` 已重新取得 server inventory，Restart 時建立的 replacement `GameEngine` 仍可能保留建立當下的舊 ToolState。

已於 `a79350941bbc93b02545be33e154a2a2dac507ca` 修正：

- Restart server session 成功後，先完成 authoritative `ToolManager.refreshInventory()`。
- 再將已經掛載中的 replacement engine 執行 `refreshFromSavedProgress()`。
- 不重建棋盤，因此不影響 Restart 的本機即時性與棋盤狀態。
- 修正 static server inventory 已經正確、但畫面上的工具按鈕仍維持舊數量的落差。
- C1 初始 UNDO、跨章累積及 Golden unlimited UNDO 規則均未修改。

目前工具鏈路已涵蓋：

1. server initial inventory
2. `getToolInventory` 的初始 UNDO 保證
3. `ToolManager.refreshInventory()` 真正 await
4. 新遊戲建立前 inventory 同步
5. Restart 新 session 後 inventory 同步
6. replacement engine 的既有 ToolState 同步
7. 工具使用仍採 local-first，透過 replay log 於 session 結束時進行 server 驗證

仍未要求經理現在單獨測試；待 Restart、UNDO、Game Over → Restart、工具累積等修正完成後一次驗證。


# 19. 移除工具數量本機假授予 fallback（2026-09-24）

進一步確認 `ToolManager` 後發現 `_initialize()` 原本存在一個不符合 server-authoritative 原則的 fallback：當 `_serverUses[type]` 為 0 時，C1 Ocean 會直接使用 `gameTool.maxUses`，等同本機自行補發 1 次 UNDO。

已於 `4f5f03ac3ef37f2ded8ab1cf3d6714b5c6dfeb87` 修正：

- ToolState 初始數量完全取自 `_serverUses`。
- 不再因 C1 而自行套用 `GameTool.maxUses`。
- 新帳號的 C1 UNDO +1 必須由 Firebase inventory initializer 提供，再由 inventory refresh 同步到遊戲。
- Firebase 明確為 0 就顯示 0，不再由本機補成 1。
- Firebase 讀取失敗時也不偽造工具數量。
- Golden 的無限 UNDO 與既有 chapter reward 規則不變。

這使工具數量來源單一化：**Server inventory → ToolManager → GameEngine ToolState**。


# 20. 修正章節工具獎勵發放時機（2026-09-24）

檢查新帳號初始工具與章節獎勵流程後，確認 `startGameSession` 原本也會發放 `chapterRewardTools(chapterIndex)`，這會造成「進入章節就先領獎」，與規則及 `completeChapter` 的完成獎勵流程不一致；完成章節時又存在獎勵邏輯，可能造成獎勵時機／數量錯亂。

已於 `26db3a2fb0d64749b2e160c18f54fa425045aafa` 修正：

- `startGameSession` 不再發放章節工具獎勵。
- 進入遊戲只負責建立 session、扣除 Life。
- 章節工具獎勵只在 `completeChapter` 通過完整 replay 驗證後發放。
- 新帳號 C1 初始 UNDO 仍由 `getToolInventory` 的 `ensureInitialUndo()` 提供 1 次。
- 因此「C1 初始 1 次 UNDO，若未使用，完成 C1 後再 +1，進入 C2 時應為 2 次」的資料流現在一致。
- `chapterRewardsClaimed` 也不再在單純進入章節時被提前標記。

這同時避免了玩家只是進入遊戲、甚至立刻離開／重開，就提前取得章節獎勵。


# 21. 修正 Server Replay 的 UNDO 分數回復（2026-09-24）

檢查 `GameEngine.useTimeRewind()` 與 Firebase `replay_validator.js` 後，發現 Client 與 Server 對 UNDO 的分數回復方式不一致：Client 會恢復到 UNDO 前的 `_previousScore`，Server 原本卻先算出本次扣除分數，再從 `previous.score` 再扣一次；當 UNDO 前已有非零分數時，Server 分數會少扣一段，造成完成章節後的 server score 與本機 score 不一致。

已於 `3a9aeaff6cf6d89450c8fbcd717f5a99b7e28c28` 修正：

- Server replay 的 UNDO 現在直接恢復 `previous.score`。
- 保留本次 UNDO 所移除的分數作為 `toolPenaltyTotal`。
- Client / Server 的 UNDO 分數結果一致。
- 不改變 UNDO 的工具庫存扣除規則。
- 不改變最高進化值：UNDO 不會讓已達成的最高進化階段倒退。

這是 server replay 驗證的一致性修正，避免玩家正常使用 UNDO 後完成章節時產生錯誤分數。


# 22. Golden 會員章節獎勵與無限 UNDO 一致性（2026-09-24）

進一步檢查 C1 完成後工具庫存同步與章節轉換流程，確認 `completeChapter` 已在伺服器完成驗證、生命退款與章節工具獎勵後，由 Client `PlayerProgressService.completeChapter()` 等待 `ToolManager.refreshInventory()`；完成畫面進入下一章時 `_startChapter()` 再使用最新 server inventory 建立新 `GameEngine`。因此 C1 完成獎勵可正常進入 C2 的工具狀態。

同時發現一個獨立的 Golden 會員邊界問題：C6 完成等章節獎勵可能是 UNDO，而 Golden 的 UNDO 本身為無限使用；原本完成章節仍會把數字 UNDO +1 寫入 Firebase。已於 `723025d54ac95a3fdffea90a7c1cdceace860196` 修正：

- Golden + UNDO 獎勵不再建立數字庫存。
- 一般會員仍照既定章節獎勵 +1。
- C1 新帳號初始 UNDO 與完成 C1 的 +1 獎勵流程不變。
- 完成章節後的工具庫存同步仍由 Firebase → `ToolManager` → 下一個 `GameEngine`。


# 23. Game Over 離場前工具庫存結算（2026-09-24）

檢查工具實際使用後的 Firebase 結算流程：Restart 已會在新 session 建立前驗證並扣除舊 session 的工具使用量；正常 Game Over → Back 原本卻把 `abandonGameSession()` 以背景非同步方式執行，畫面先回 Home，Home 的 inventory refresh 可能早於 Firebase 結算完成，造成短暫顯示舊工具數量。

已於 `61bbc3cff7835aaff5f9bec2ee97ae0fec1483c5` 修正：

- Game Over → Back 先清除本機該局存檔。
- 等待 `abandonGameSession()` 完成工具使用結算。
- 完成後才返回 Home。
- Home 再刷新時可直接取得已結算的 Firebase 工具庫存。
- 不影響遊戲內工具使用的 local-first 即時操作。
- 不改變 Golden 無限 UNDO 規則。

目前 Restart / Game Over 結束路徑的工具使用，都已納入 server replay 驗證與 inventory 結算。


# 24. UNDO 分數規則再次校正（2026-09-24）

進一步交叉檢查 Client `GameEngine._restorePreviousState()` 與 Server `replay_validator.js` 後，確認專案既定實作並非「完全恢復到 UNDO 前分數」，而是：恢復 UNDO 前棋盤，同時扣除被撤銷那一步所取得的分數作為工具代價。Client 實際公式為 `previousScore - revertedScore`，因此前一輪 Server 改成直接 `previous.score` 反而會造成兩端不一致。

已於 `7bcc5a7569bff195e55e534d7680e5e1a409bfbe` 校正回一致規則：

- Server UNDO 分數 = `max(0, previous.score - revertedScore)`。
- Client / Server UNDO 分數公式一致。
- `toolPenaltyTotal` 仍記錄被撤銷的分數增量。
- 本次只修正一致性，不改變玩家既有工具規則。


# 25. 修正章節獎勵覆蓋工具扣除（2026-09-24）

檢查同一個 `completeChapter` transaction 內的工具使用結算與章節獎勵時，發現一個實際庫存錯誤：若玩家在該章節使用了「本章完成獎勵的同一種工具」，先計算出的 `toolUpdates` 扣除值會被後面的獎勵邏輯重新以原始 `toolInventory + 1` 覆蓋，導致該工具本局使用量沒有真正扣掉。

例如 C1：初始 UNDO 1，使用 1 次後完成，正確結果應為 `1 - 1 + 1 = 1`；原程式可能變成 `1 + 1 = 2`。

已於 `19751a5cbe0b75a1e5e49502a16533d8a7e60d73` 修正：

- 章節獎勵先讀取同一 transaction 已計算的 `toolUpdates`。
- 若該工具本局已扣除，獎勵會加在扣除後的數量上。
- Golden 無限 UNDO 仍不建立數字庫存。
- C1 未使用 UNDO：`1 → 2`。
- C1 使用一次 UNDO：`1 → 0 → +1 = 1`。
- 避免 Restart / Game Over / Completion replay 結算時出現庫存憑空增加。


# 26. 防止過期 Restart 回應覆蓋最新 Session（2026-09-24）

檢查 UNDO / ReplayLog / autosave / Restart / Game Over 的重複結算流程後，確認 Server 端以 session status + transaction 保護，同一 session 第一次結算後再次結算不會再次扣工具；工具使用量以 replay 結果與 session 已結算 `toolUsage` 的 delta 計算，因此正常重複呼叫不會重複扣除。

另外發現 Client `restartGameSession()` 在 Firebase 回應回來後原本沒有再次檢查 operation generation。若極端情況下另一個較新的 session 操作已經開始，舊 Restart 回應可能覆蓋最新的本機 session binding。

已於 `dfe518de035fc1d8bacb4a0d142d7ee19b1a2956` 修正：

- Restart Firebase 回應套用前再次驗證 `_sessionOperationGeneration`。
- 舊操作的回應不再覆蓋新操作的 Session ID。
- 不改變 Server transaction 與工具結算規則。


# 27. 防止清除存檔與舊 Autosave 競態（2026-09-24）

檢查 Home → 選章節 → Game Over / 離開 → 新局的 Life、Session、Cached Save 交界後，找到一個實際的本機存檔競態：`SaveManager.save()` 已有序列化佇列，但 `clearChapter()` 原本直接寫入 SharedPreferences，可能被前面尚未完成的舊 GameEngine autosave 隨後覆寫，造成已結束的舊棋盤重新出現；`clearGameSessionId()` 也存在相同的非佇列寫入風險。

已於 `5568054` 修正：

- `clearChapter()` 改為加入同一個 `_saveQueue`。
- 實際清除移至 `_clearChapterNow()`，確保所有舊 autosave 先完成後才清除。
- `clearGameSessionId()` 同樣加入 `_saveQueue`，避免 Session ID 清除被舊寫入競態影響。
- 保留既有 local-first 設計，不讓正常遊戲操作等待 Firebase。

這一修正直接針對先前「新棋盤出現後舊棋盤又回來」以及「離開後舊局可能再次被載入」的本機存檔競態。


# 28. 防止舊 GameEngine Autosave 覆寫新 Session（2026-09-24）

進一步檢查 Home → 進局 → Restart / Game Over → 離開的 Life、Session、Cached Save 邊界，發現另一個實際競態：雖然 `SaveManager` 已將所有寫入序列化，但原本每次 `_saveNow()` 都會直接使用當下的全域 `gameSessionId`。因此舊 GameEngine 在 Session 替換後才完成的 autosave，可能把「舊棋盤」配上「新 Session ID」寫回本機，造成新局之後舊棋盤再次被載入。

已修正：

- `ab6f44d` — `GameEngine.createSaveData()` 將建立 snapshot 當下的 `gameSessionId` 一併保存。
- `5ff0d69` — `SaveManager._saveNow()` 對明確綁定 Session 的 snapshot 做一致性檢查；snapshot Session ID 與目前全域 Session 不一致時直接丟棄。
- 這讓舊 Engine 的延遲 autosave 無法在 Restart / 新局 Session 替換後復活舊棋盤。
- 新 Engine 在 Firebase Session 替換完成前產生的舊綁定 snapshot，也不會覆寫後續已 rebind 的新 Session snapshot。

目前 Home / Game 的 local-first 方向維持不變：遊戲操作不等待 Firebase，但本機 snapshot 必須始終與當前 server-owned Game Session 綁定。


# 29. 忽略失效的未完成章節本機綁定（2026-09-24）

檢查 Home 的 unfinished chapter 判定後發現：原本只要某章本機 snapshot 有 `gameSessionId`，就會被視為未完成章節；但該 Session 可能已經被 Restart、離開、完成或其他流程替換。這會讓 Home 被失效的舊 snapshot 鎖住，甚至與 Firebase 當前 active session 不一致。

已修正：

- `unfinishedChapter` 現在要求 snapshot 的 `gameSessionId` 必須等於 `SaveManager.gameSessionId`。
- 舊 Session 的殘留 snapshot 不再阻止玩家選擇當前有效章節。
- 配合前面 Session-bound autosave 防護，形成「snapshot → current session → Home unfinished chapter」一致性鏈。


# 30. 防止 Resume 舊回應覆寫新 Session（2026-09-24）

- `resumeGameSession()` 現在啟動時立即遞增 `_sessionOperationGeneration`。

- 與既有 Start / Restart stale-response 防護統一。


# 31. Home 依 Server Active Session 限制章節切換（2026-09-24）

檢查 Home 與 PlayerProgressService 的 server/local session 邊界後，確認 Home 原本只依賴本機 `unfinishedChapter` 阻止章節切換。若 Firebase 仍有 active session、但本機棋盤 snapshot 缺失或失效，Home 仍可能讓玩家點入另一章；進入 Game Page 後才因 active chapter 不符而拒絕，形成無法正常遊玩的死畫面。

- 本機 unfinished guard 與 server active-session guard 並存，避免 local/server 任一側存在未結束局時錯誤切章。
