## 已確認的風險與尚未完成事項

### 1. 本機遊戲資料尚未完整依 UID 隔離

`lib/game/services/save_manager.dart` 目前仍使用共用的 `rebirth_2048_local_save_v1` 與 `rebirth_2048_game_session_id_v1`，沒有以 Firebase UID 作為 key namespace。雖然 snapshot 有 server session ID 綁定及序列化 save queue，仍不足以證明帳號 A 登出後帳號 B 不會讀取或影響 A 的本機存檔。

登出流程 `lib/screens/personal_page.dart` 會清除工具、生命、Gold 的快取並呼叫 Firebase Auth signOut，但沒有明確執行本機存檔 UID 切換。不得用無條件刪除存檔的方式草率修正，因為可能破壞尚未完成的棋盤或 RESET 復原資料。下一步應設計 UID-scoped snapshot/session key、明確的 legacy snapshot 歸屬/遷移規則，以及舊引擎延遲 autosave 的所有權防護，再加入測試。

### 2. Firestore Rules 尚未有 Emulator allow/deny 測試

目前 `firebase.json` 指向根目錄 `firestore.rules` 與 `firestore.indexes.json`。後端 CI 有 Node 靜態契約及單元測試，但尚未確認有使用 Firebase Emulator / Rules Unit Testing 執行的真實 allow/deny 規則測試。需要新增可在 CI 重複執行的測試，至少驗證：
- 未登入使用者不能讀寫受保護資料；
- 使用者不能直接寫入自己的權威 session、wallet、membership、purchase 與 security 資料；
- 不能跨 UID 存取其他使用者資料；
- callable-only 支援訊息與 pending operation 路徑不允許客戶端直接操作；
- 規則允許的必要讀取路徑仍可正常使用。

### 3. 商城付款驗證仍未完成

`submitPurchaseForVerification` 目前只建立 pending verification 記錄，不會因客戶端提供 transaction ID 就直接發 Gold 或會員權益。真正的 Google Play / Apple 伺服器端驗證與驗證成功後發放權益仍未完成；在可信任的商店驗證能力及憑證配置未具備前，必須維持 fail-closed，不能模擬成功或發放權益。

## RESET / 存檔競態的既有保護

- RESET 透過持久化 pending payload 與穩定 operation ID，在重試時使用後端 operation receipt 避免重複扣生命。
- 不確定 RESET 結果時會保留 payload 並鎖定遊戲互動；返回時不執行一般 save/abandon 流程，留待下次進入復原。
- `SaveManager.clear()` 已串接 `_saveQueue`，避免先前排隊的 autosave 在 clear 之後覆寫資料；但仍需檢查舊引擎是否能在 clear 完成後再排入新 save。
