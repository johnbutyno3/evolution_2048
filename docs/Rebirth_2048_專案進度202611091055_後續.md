## 本次完成

### 1. 依後端 active session 選擇正確的本機快照
- `SaveManager.restoreSnapshotForSession()` 會檢查 A/B 兩份快照，依章節及 `gameSessionId` 找出與後端 active session 相符的版本。
- 找到後更新 active-slot pointer、本機快照快取及 session binding。
- 已避免每次 refresh 都重複寫入相同 pointer／binding。
- `PlayerProgressService.refresh()` 取得帳號快照後，會依後端 active session ID 選擇本機快照。
- 若後端沒有 ACTIVE session，但本機只剩帶有 session ID 的未完成孤立棋盤，進入遊戲時不再把它誤當成可恢復的有效局。

### 2. Restart／下一章切換的中斷復原
- Restart 前先停止並 flush 舊棋盤，再建立新棋盤。
- 新棋盤先寫入另一份快照並綁定新 gameId，再呼叫 Supabase RPC；舊棋盤仍保留在另一份快照。
- 後端確認成功時，refresh 會選取新 gameId 對應的快照。
- 後端確認未成功時，refresh 會選回舊 gameId 對應的快照。
- 若網路結果不明，畫面維持鎖定，不允許繼續操作或錯誤 abandon；返回首頁後由下一次帳號 refresh 依後端 active session 選擇正確快照。
- 下一章建立新 Session 也採相同的先保存後呼叫流程。
- GameEngine 可在不再次寫入快照的情況下停止計時器，避免未知狀態時覆寫另一份復原資料。
- 移動、鍵盤、拖曳及工具操作在 Restart 結果未確定時會被阻止。

### 3. 一般新局建立
- `startGameSession` 接受初始本機存檔，先寫入並綁定預期 gameId，再以背景方式呼叫 Supabase。
- 遊戲頁等待的是本機存檔完成，不等待網路回應才顯示棋盤。
- 後端成功時，以 active session ID 對應本機快照；明確拒絕時才回復原畫面。
- pending start 的結果會保留至呼叫端完成核對，避免 Future 太早清除而丟失結果。
- 重複呼叫若沒有相同的本機棋盤／請求識別資料，會 fail closed，不會錯誤回報已建立。

### 4. Restart 後端冪等性修正
新增 migration：`supabase/migrations/20261109113000_restart_idempotency_payload_guard.sql`

- 已存在 requestId 時，先核對 gameId、章節、初始棋盤。
- 再核對 abandon event ID、previousGameId、事件種類及完整 payload。
- 若 abandon event 已存在但 requestId 不同，直接拒絕；避免重用舊 abandon event 建立另一個不扣 Life 的 replacement session。
- 所有檢查在呼叫 abandon settlement 前完成。
- Edge Function 將 request/event payload 衝突映射為 HTTP 409 `IDEMPOTENCY_CONFLICT`。
- Restart 保留原局已扣除的 Life，不再額外扣一次；`supabase/README.md` 已同步修正。
