## 規格與實作差距（部署前必須處理）

### A. 離線遊戲與新局建立

正式規則要求本機優先、移動與動畫不等待後端；新局逾時時可先在本機保存唯一 requestId、gameId、生命扣除紀錄及待同步事件，連線恢復後再核對。

目前 `start_game_session` 必須先呼叫 Supabase RPC，並在同一交易內扣除 FREE 生命、建立伺服器 session。若 APP 直接把這個回應當成開始遊戲的必要條件，離線時便無法建立新局，與本機優先規則不一致。需要設計本機先行、事件持久化、後端冪等補同步的流程；不得將此問題誤當成「交易必須在線」規則。會員／Gold／工具購買交易仍必須在線驗證。

### B. 工具庫存結算時機

目前 `finish_game_chapter` 才依回放結果扣除工具庫存；`save_game_checkpoint` 只保存 checkpoint，未看到 Game Over／放棄結束流程的工具結算 RPC。若一局使用工具後沒有成功過關，可能未完成後端工具扣除。需設計適用於 Game Over、放棄及完成的冪等結算方式，並以服務端可驗證資料為準，不能只相信任意客戶端庫存數字。

### C. 回放驗證覆蓋率

目前四個 Deno 測試覆蓋初始棋盤不一致、未完成章節、事件數上限與章節工具權限。尚未覆蓋完整移動／生成、UNDO、各工具、非法數值、重複事件、併發結算、種子／生成序列一致性及真實 SQL 原子性。現有測試通過不代表反作弊完整。

### D. Flutter 尚未完成 Supabase 身分遷移

GitHub 來源的 `lib/main.dart` 仍初始化 Firebase Core、Firebase Auth、Firebase App Check，首頁仍使用 Firebase Auth 狀態流。Supabase 初始化目前只是逐服務導入的過渡層。不能在所有 Firebase 呼叫點遷移、登入方式驗證及 APP 流程測試前移除 Firebase 套件。

## 規則基準

- APP 啟動／登入後，必須向後端確認會員資格及生命、Gold、工具權益；不能用舊快取覆蓋權威資料。
- 會員、Gold、工具等購買交易必須在線驗證及同步；離線時警告並禁止交易。
- 一般遊戲操作可離線進行，本機每次有效操作立即保存；重要事件以持久化佇列同步、重試及去重。
- FREE 生命上限 5、每 40 分鐘恢復 1 條；過關退還本局扣除的 1 條但總數最高仍為 5。
- 會員、Gold、工具、永久章節進度及商店交易不得由前端任意覆寫。
- 被鎖帳號仍須保有客服與申訴入口。
