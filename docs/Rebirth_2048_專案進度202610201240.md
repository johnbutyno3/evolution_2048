# Rebirth 2048 專案進度 — 2026-10-20 12:40

## 避免 RESET 在持久化前覆蓋舊棋盤

本輪審查發現：RESET 先把新 Engine 設成活動棋盤並啟動計時器，之後才保存 pending payload。若 payload 寫入失敗或程序剛好中斷，舊棋盤可能先被新棋盤的本機自動保存覆蓋，而後端其實還沒收到 RESET。

已修正順序：

1. 建立新棋盤，但暫不替換活動 Engine、不啟動新棋盤計時器。
2. 先保存包含原請求、operation ID 與新棋盤快照的 pending payload。
3. 只有持久化成功後，才切換到新 Engine 並呼叫後端。
4. 若持久化失敗，保留原活動棋盤並恢復生命／工具狀態，不再把未提交的新棋盤寫入舊 session。

已新增 callable contract 測試，確認新 Engine 的切換發生在 pending payload 寫入之後、後端 callable 之前。
