## 1. 絕對開發規則

### 1. 作業守則：

#### 1. 新對話啟動時，比對 GPT `/2048/` 與 Git `docs/` 的規則以及進度檔案的最新日期時間版本。
     2. 一律以日期時間最新的檔案為準作為 Source of Truth，不因儲存位置不同而優先使用舊版本。
     3. 讀取最新專案規則。
     4. 讀取最新專案進度。
     5. 檢查 GitHub 最新 committed state。
     6. 確認目前未完成工作。
     7. 直接繼續下一項，不要求專案經理重新說明已完成內容。
     8. 注意GPT限制，預估限制時間快到，GPT快要要求開新對話前，提前告知經理，並先更新規則與進度並提供經理新對話銜接指令。
     9. 規則／進度版本判定

### 2. 規則與進度檔案管理：
#### 1. 目前規則及進度檔案儲存位置有兩個：
        - GPT 檔案庫 `/2048/`
        - Git 專案 `docs/`
     2. 兩邊若存在日期時間版本檔，若最新版本位於 Git `docs/`，而 GPT 檔案庫暫時無法寫入，Git 版本即為目前工作基準，直到檔案庫恢復並完成同步。
     3. 本機同步原則：
##### 1. GPT 檔案庫 `/2048/` 暫時無法建立檔案時，不得停工，也不得宣稱已完成檔案庫同步。
         此時將最新規則／進度先保存於 Git 專案 `docs/`。
      2. 檔名使用 "Rebirth_2048_專案規則",後面加上`YYYYMMDDHHMM` 版本時間。例：Rebirth_2048_專案規則202609151030
-     3. 當GPT檔案庫恢復寫入能力，再將最新版本新增至 `/2048/`。
      4. 規則或進度更新時，須建立新檔(檔名建立規則如上2.)，不可刪除原始資料，建立新的時間戳檔，不覆蓋舊檔。
      5. 規則或進度建立新檔時，內容以上最新版本內容加上更新資訊，不可刪除原本資料以維護資料完整。
      6. **重要：Git fallback 文件必須延續 File Library 最新完整版本，不得改成短摘要或只保存增量片段。**
      7. 專案經理會適時手動調整、搬移文件，以確保文件之完整以及最新版本。
      8. 例：本次 2026-09-16 文件狀態
         - `docs/Rebirth_2048_專案進度202609161200.md` 已移除，不得恢復。
         - 四份已整合舊文件已從 GitHub 刪除。
         - 本機已同步至 `f0a0eb5`，`git status --short` 為空。
         - `Rebirth_2048_專案規則202609161256.md` 曾建立，但缺少上述三組完整工作流程條款；因此 `202609161300` 版本正式取代其規則有效性。
         - `Rebirth_2048_專案規則202609161300.md` 為上一版 Git fallback 的完整規則版本。
         - `202609161615` 版本在完整延續上一版所有規則的基礎上，正式新增終端機工作階段安全條款。
         - 待 File Library 恢復寫入能力後，必須將本完整版本新增至 `/2048/`，不得只同步新增條款。


### 3. 專案經理工作量最小化

#### 1. 可以由GPT透過 GitHub／Git 完成的工作，例如直接檢查、修改、建立文件、Git作業與驗證，應由GPT直接進行。
     2. 只有權限不足、工具無法執行或必須依賴本機環境驗證時，才告知專案經理(對話者)執行。
     3. 須由經理執行時，必須提供完整可直接執行指令，不得要求經理自行查找。
     4. 專案經理執行後，GPT 負責後續讀取、檢查、驗證與整理。

### 4. GPT 自主作業原則

####1. 以 GPT 自己處理為原則，盡可能由 GPT 直接完成檢查、修改、建立文件、Git 作業與驗證。
    2. 本機不是第一作業位置。工作以 Git 為主,因此不得以讀取不到本機為理由，要求經理執行；
    3. 當一個工作段落完成並確認後，再要求／安排同步到本機。
    4. 本機同步後仍以 GitHub committed state 判定完成狀態。
    

### 5. 大型 GitHub 檔案分段讀取規則（2026-09-16 新增）

#### 1. 大型檔案不得因單次輸出截斷而停止處理或要求經理手動處理：
        GitHub 大型來源檔案若單次讀取結果被工具輸出限制截斷，不得因此判定檔案無法處理，也不得改用不完整內容重建檔案。
     2. 必須使用同一版本的分段讀取，先取得目前檔案的實際 blob SHA／版本，再以相同 ref 或相同 blob 對檔案進行多段 line-range 讀取，例如：
      - 1–300
      - 301–600
      - 601–900
      - 901–1200
      實際分段大小依檔案長度與工具輸出限制調整。
     3. 分段結果必須完整覆蓋來源，所有分段必須連續、無遺漏、無重疊造成內容誤判，直到完整取得大型來源檔案的實際內容。
        若最後一段不足預估行數，以實際 EOF 為準。
     4. 只能以完整內容修改：完成所有分段讀取後，GPT 必須在掌握完整且未截斷的原始內容後才能建立新的 blob、更新檔案或建立 commit。
        任何一段缺失時，不得覆蓋原檔。
     5. 修改前後都要做實際比對，修改大型檔案後，必須確認：
##### 1. 原檔 blob SHA 與修改前版本一致。
      2. 修改只包含本次明確任務所需內容。
      3. 沒有因分段重組遺失、重複或改變其他內容。
      4. Git commit diff 可清楚呈現預期變更。
      5. 與 Git-first 規則共同適用：
         大型檔案仍優先由 GPT 直接在 GitHub 處理；不得因檔案較大就把可由 GPT 完成的工作轉嫁給專案經理。
         只有工具或權限確實不足時，才要求本機協助。
      6. 實例：本次實際採用：
         本次 `functions/index.js` 原始 blob `a9d7198feb9a404e9f3158bf77aec9686e52ee23` 已先完整取得後修改；
         變更僅為加入 Security Enforcement import，以及在 8 個敏感 callable 加入 `enforceSensitiveOperation` gate。
         完成後以 Git commit diff 再次核對，避免截斷覆蓋問題。

    

### 6. 終端機工作階段安全規則（2026-09-16 新增）

#### 1. 提供 PowerShell 指令時，必須以「執行完成後仍留在目前 PowerShell 工作階段」為基本要求。
        若某項操作可能改變或終止目前工作階段，GPT 必須改用不影響工作階段的安全寫法。
        絕對禁止提供任何會關閉、終止、殺掉、重啟或替換目前 PowerShell／Terminal 工作階段的指令或操作方式。
     2. 明確禁止的終止方式：不得提供或建議：
       - `exit`
       - `Stop-Process`
       - `taskkill`
       - 關閉目前 PowerShell／Terminal 視窗的指令
       - 任何等效於終止目前終端機工作階段的命令、腳本或替代寫法
     3. 錯誤處理，如果本機修改、語法檢查、Flutter analyze、Git 檢查或其他命令失敗：
       - 保留目前 PowerShell／Terminal 工作階段。
       - 只輸出失敗原因與下一步處理方式。
       - 不得用關閉終端機方式處理錯誤。
       - 不得要求專案經理重新開一個終端機作為一般錯誤處理手段。
     4. 本規則與既有 Git-first 規則同時適用：
        優先由 GPT 直接在 GitHub／Git 完成工作；只有確實需要本機操作時才提供 PowerShell。
        即使必須使用 PowerShell，也不得以任何方式關閉目前終端機工作階段。


Rebirth 2048

  
1. 項目標識
 
Rebirth 2048 是一款使用 Flutter 建構的 4×4 生物演化/生態系統復興遊戲。
 
核心概念：
 
玩家扮演的是一個人工智慧，正在模擬地球的過去現在及未來…。
- 此棋盤採用 2048 式的移動和合併機制。
- 生物影像是主要的圖塊視覺元素。
- 數值為遊戲內部數值。
- 遊戲包含六個權威章節。
- 本地保存的資料是恢復資料。
- 受保護的進度、錢包、會員資格、工具和安全敏感狀態由伺服器權威控制。
- Chrome 是目前實際桌面測試的目標瀏覽器。
 
技術：
 
- Flutter 3.44.6
- Dart 3.12.2
- Firebase
- Firestore
- Firebase 身份驗證
雲函數
- 國際化目前主要以英語和繁體中文為主。

# 重生2048六章內容規格
 
本文件是目前遊戲六章的正式內容基準。中文內容為確認基準；實際遊戲顯示需透過在地化依使用者語言顯示。
 
##核心規則
 
-共6章。
-每章必須合成出該章最高階物件才算過關。
-不存在「2048即通關、4096額外挑戰」的規則。
-每章的最高階依該章階數逐級成長。
-每個階級的「首次產生」只觸發一次新階級回饋：震動+4×4棋盤上方新物件名稱，並維持顯示直到升階後被替換。(上方說明維持在當下最高階)
-同一階級之後再次產生，不再重複震動與更不許改變當下最高階名稱。
-不同章節的首次發現紀錄應分開計算。
-顯示時不得影響玩家操作。
-說明文字必須走在地化，不能寫死單一語言。
##最高階過關動畫
 當該章最高階物件產生時，**不得直接跳過物件畫面進入過關畫面**。
 正確流程：
 第二高階兩個物件合成
↓
產生最高階物件圖片出現
↓
圖片移到中央並由小慢慢放大
↓
動畫完成但圖片維持不可以消失
↓
轉到章節完結過關畫面
↓
顯示過關說明及選項

#7.計分規則
 
-合成產生新物件時取得其合成階分數。，比如2+2，合併產生4，加4分，而128+128則合併產生256，加256分。
-使用工具會扣除分數。
-工具扣分基準：
UNDO，扣除上一步所得分數，例如得256分後UNDO，立即扣256分。
REMOVE，扣除移除項目階數，例如移除一個128，立即扣128分
 SWAP，扣除交換兩個階數總和，例如將32跟128交換，扣除160分
DUPLICATE，扣除複製項目分數，例如複製1024，則扣1028分。
-分數最低為0，不顯示負分。
 

#8. 排行榜核心是最終分數。
