# 10. 本輪新增修正（Save race）

發現 Restart 閃回舊棋盤仍可能來自 local autosave race：舊 GameEngine 與新 GameEngine 各自排程 SaveManager.save，兩條寫入路徑可能交錯，導致舊 snapshot 最後覆蓋新棋盤。

已於 `685866143fe81bded76a7ae9942284f88dfe21ca` 修正：

- SaveManager 所有 snapshot write 改為全域序列化 queue。
- 舊 engine queued autosave 不會再與新 engine save 同時競爭。
- Restart 新 session rebinding 與 local save serialization 現在同時受保護。
- 此項仍待與 Restart / Game Over → Restart 一次實機驗證。

# 18. Session 退款交易中的 Life 自動恢復事件補齊（2026-09-24）

繼續檢查 Life → Session settlement 後，發現 `abandonGameSession` 的 unfinished-exit 退款交易有一個事件紀錄缺口：它會在同一筆 transaction 內先依目前時間計算已到期的自動恢復，再退款 +1 Life，但原本只更新 Life state，沒有寫入 `life_regeneration` event。

已於 `73835a970823604a4753321baa88b4fa3eaba1d3` 修正：

- `refundLifeInTransaction()` 現在會記錄本次交易實際發生的自動恢復數量。
- 事件包含 `beforeLives / afterLives / amount`，並使用與 `life.js` 相同的 deterministic event ID，避免 Firestore transaction retry 重複記錄。
- 退款本身仍只是 unfinished exit 的 +1，不會被誤記成自動恢復。
- Game Over 不退款的規則不變。
- 不增加玩家正常遊戲操作的網路等待。

目前繼續檢查 tool usage 在 Restart / abandon / completion 三條 settlement 路徑是否完全一致。

# 19. Session 工具結算與 Chapter Complete Life 事件檢查（2026-09-24）

本輪針對一般會員 UNDO（timeRewind）在 Restart、unfinished exit、Game Over、Chapter Complete 四條 settlement 路徑逐一檢查。

## UNDO / Tool settlement 結果

- replay_validator.js 對每局 replay 只累計實際 timeRewind event，不會額外從 client tool cache 合成一次使用。
- Restart / abandon / complete 都以 totalUses - settledUses 計算本次尚未結算的工具使用量。
- 同一 session 已結算後會進入非 active 狀態；再次 settlement 不會再次扣除 inventory。
- Golden 的 timeRewind 會在 server settlement 排除數字 inventory 扣除，符合 unlimited UNDO 規則。
- Chapter reward 會建立在本次已扣除的 toolUpdates 上，不會把同一個工具的本次消耗覆蓋掉。
- 因此目前沒有發現「一般會員一次 UNDO 被 settlement 重扣」的程式錯誤，不新增無必要的工具扣除修改。

## Chapter Complete Life regeneration event

檢查時發現另一個一致性缺口：completeChapter 在完成交易內會先套用已到期的 Life 自動恢復，再退款完成本局消耗的 1 Life，但原本沒有寫入 life_regeneration event。

已於 7875826d0350a87a98eeb16fb8792d0b8d6e7bec 修正：

- 完成交易現在會計算本次實際恢復的 Life 數量。
- 有恢復時寫入 users/{uid}/life_events/{eventId}。
- event 使用 deterministic ID，避免 Firestore transaction retry 重複記錄。
- beforeLives / afterLives / amount 只記錄自動恢復，不把 Chapter Complete 的 +1 refund 混入 regeneration event。
- Chapter completion 的 Life refund 規則不變。
- 不增加玩家進入遊戲或正常操作時的網路等待。

## 下一步

目前 Session / Tool settlement 已完成程式檢查；下一個安全性邊界是確認 replay 是否與實際新局起始狀態綁定，避免 client 自行提供另一組合法 initialTiles 而讓 server 只驗證「合法 replay」而非「這一局實際發生的 replay」。

# 20. Replay 與實際 Game Session 初始棋盤綁定（2026-09-24）

本輪檢查發現原本 server 只驗證 replayLog 本身是合法的 2048 replay，卻沒有確認 replay 的 initialTiles 就是該 Game Session 實際建立時使用的初始棋盤。這留下 client 偽造另一組合法兩格 2/4 初始棋盤的空間。

已完成修正：

- replay_validator 新增 expectedInitialTiles，比對 replay initialTiles 與 server session 綁定的 initialTiles。
- startGameSession 現在要求合法的 16 格、恰好兩格 2/4 初始棋盤，並將其寫入 session。
- restartGameSession 同樣要求並綁定新的初始棋盤；舊 session 的 replay 會以舊 session initialTiles 驗證。
- abandonGameSession 與 completeChapter 的 replay settlement 都改為以 session.initialTiles 驗證。
- Flutter 新局會先建立實際要顯示的 local board，再把同一組 initialTiles 傳給背景 session transaction；因此仍維持 local-first，不等待 Firebase 才建立棋盤。
- Game Over / Restart 與 Chapter 切換建立的新棋盤，也使用同一組送給 server 綁定的 initialTiles。
